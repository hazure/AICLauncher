Alice in Cradle 安卓端兼容补丁

让 Windows 版《Alice in Cradle》(v0.30) 在安卓转译容器（Winlator、Termux-X11、Box64 + Wine）中正常启动、稳定运行的本地补丁与辅助脚本。

开始使用 遇到问题

这个仓库解决什么问题

原版 Windows 游戏在安卓转译环境（Wine / Box64）中运行时，常出现启动拦截、闪退或严重卡顿：一方面游戏的完整性与运行环境校验会把转译层识别为异常环境，另一方面资源哈希校验会阻止被修改过的可执行文件加载。本仓库提供一套纯本地的修补与启动方案：

替换启动器

src/stub_perfect.c 精简启动器源码，编译后替换 AliceInCradle.exe，兼容安卓 Wine / Box64 启动并透传命令行参数。

环境校验补丁

patch_unsafeAssem.py 修补 unsafeAssem.dll 的环境校验，自动备份 .orig 并同步 StreamingAssets/_sha.txt。

一键启动

launcher.sh 为安卓 / Wine 容器补全 Box64、DXVK 与着色器缓存配置，且不覆盖 Winlator 中已设好的参数。

可选增强

unmosaic.py 可选去马赛克（修补 Assembly-CSharp.dll，支持 --restore 还原）；update_sha.py 单独重算哈希清单。

重要前提：本仓库不包含任何游戏本体或资源文件。请先通过官方渠道购买正版游戏，再在本机游戏目录上执行以下操作。

目录结构

路径作用是否需要修改
src/stub_perfect.c精简启动器 C 源码，编译产物用于替换 AliceInCradle.exe一般无需修改
patch_unsafeAssem.py修补 unsafeAssem.dll 环境校验并同步哈希清单直接运行
launcher.sh容器启动脚本，补全 Box64 / DXVK / 着色器缓存可直接运行或按需微调
unmosaic.py可选：去马赛克，可 --restore 还原按需运行

docs/完整文档（本文档站的源内容）只读
tests/补丁与脚本的自测用例只读

快速上手

从准备环境到进入游戏，通常 15 分钟内可完成。核心动作只有三步：替换启动器、打补丁、启动。

0. 准备条件

  • 正版《Alice in Cradle》v0.30 Windows 版游戏目录（建议路径不含中文与空格）。
  • 一个可用的安卓转译容器：Winlator（推荐，配置最省事）、Termux + Wine + Box64 或等价的 Box64 + Wine 组合。
  • Android 端可用的 python3（Termux 内 pkg install python）与 clang（用于本地编译；若在 PC 上交叉编译则需要 x86_64-w64-mingw32-clang）。
  • 游戏目录与存档：动手前先整目录备份，脚本会覆盖 AliceInCradle.exe 与 DLL。

1. 指定游戏目录

所有脚本共用同一个环境变量 AIC_GAME_DIR，指向游戏根目录（内含 AliceInCradle.exe 与 StreamingAssets/）。

export AIC_GAME_DIR="/path/to/AliceInCradle_ver030"
shell
校验：执行 ls "$AIC_GAME_DIR" 应能看到 AliceInCradle.exe、AliceInCradle_Data/、unsafeAssem.dll、StreamingAssets/。看不到请把路径改对再继续。

2. 编译精简启动器并替换 AliceInCradle.exe

在 PC（Linux / WSL）上交叉编译出 Windows 64 位可执行文件，直接写到游戏目录：

x86_64-w64-mingw32-clang -O2 -s -mwindows -nostdlib \
  -Wl,-e,WinMainCRTStartup \
  -o "$AIC_GAME_DIR/AliceInCradle.exe" \
  src/stub_perfect.c -lkernel32 -luser32
shell
覆盖前务必备份原始 AliceInCradle.exe（复制到游戏目录之外）。这份 stub 会完全替代原启动器，回退需要还原原始文件。

3. 打环境校验补丁

修补 unsafeAssem.dll，脚本会自动生成 .orig 备份并同步 StreamingAssets/_sha.txt：

python3 patch_unsafeAssem.py

# 第三方 Mod 与补丁共存时
python3 patch_unsafeAssem.py --target "$AIC_GAME_DIR"
python3 patch_unsafeAssem.py --force-skip-sha
shell

4. 启动游戏

./launcher.sh          # 容器内命令行启动
# 或：直接在 Winlator 容器里点 Start 启动 AliceInCradle.exe
shell

5. 可选操作

python3 unmosaic.py     # 去马赛克（修补 Assembly-CSharp.dll，--restore 可还原）
python3 update_sha.py   # 全量重算并同步 _sha.txt
shell

推荐操作顺序

顺序动作完成后应看到
1备份整个游戏目录目录外存在一份完整副本
2编译并替换 AliceInCradle.exe文件体积明显变小（KB 量级）
3运行 patch_unsafeAssem.py出现 unsafeAssem.dll.orig，哈希清单被更新
4运行 launcher.sh 或容器内启动进入 Unity 启动画面并可到主菜单
5（可选）unmosaic.py 后重跑 update_sha.py补丁生效且不再报完整性错误

安卓驱动与性能设置

Unity 游戏在转译层的主要瓶颈是图形驱动与 JIT/动态翻译效率。这一节给出 Turnip、DXVK、Box64 三条常见的调优路径。

Turnip 显卡驱动

  • 骁龙 Adreno GPU 优先选 Turnip（Vulkan 路径），比 virgl/OpenGL 转发明显更快、兼容性也更好；首次进入主菜单时着色器编译会有停顿，属正常现象。
  • 分辨率：Unity 游戏在 1280x720 或 1600x900 下通常最稳；过高分辨率会让移动 GPU 在转译层快速失速。
  • 若画面出现贴图错乱、黑屏或驱动崩溃，先切回较低分辨率并关闭 MSAA / 后期特效，再考虑更换 Turnip 版本。

DXVK 与着色器缓存

  • D3D9 / D3D11 调用经 DXVK 转成 Vulkan；首次运行会做着色器编译（表现为进游戏前明显卡一段时间）。
  • 把着色器缓存目录放到持久化、可读写的路径（例如容器内 ~/.cache/dxvk），不要把缓存放进每次重置的临时目录，否则每次都要重编。
  • 可选环境变量用于改善流畅度：异步着色器与 HUD 调试（按需开启）。
export DXVK_STATE_CACHE_PATH="$HOME/.cache/dxvk"
export DXVK_ASYNC=1          # 异步编译着色器，减少卡顿尖峰
# export DXVK_HUD=compiler   # 排查着色器编译时临时打开
shell

Box64 动态翻译

Box64 的动态重编译（dynarec）是性能关键。launcher.sh 会补全这些配置，并保留 Winlator 容器里已设好的参数：

变量常见取值说明
BOX64_DYNAREC1启用动态重编译，性能的主要来源
BOX64_DYNAREC_STRONGMEM1 / 2加强内存模型模拟；偶发崩溃或数值异常时提高
BOX64_DYNAREC_SAFEFLAGS1 / 2标志位保守度；闪退时调高换取稳定性
BOX64_DYNAREC_FASTROUND0关闭快速取整，修图形/物理的精度抖动
BOX64_DYNAREC_X87DOUBLE1x87 用双精度，处理浮点异常时打开
BOX64_LOG1 / 2排查用日志，正式游玩时关掉以减少开销
调优原则：一次只改一个变量并记录结果。稳定性优先于帧率——先确保能进游戏、能存档，再逐步回调参数提性能。

容器通用建议

  • 给容器分配 4 GB 以上内存，并开启 swap；Unity 资源解包时内存压力较大。
  • 游戏目录挂载为可读写，且避免放在只读或每次重置的路径（会破坏存档与哈希清单）。
  • 关闭后台高负载应用；移动端温控降频会让帧率剧烈波动。
  • 首次进入前把游戏画质设为中低、关闭垂直同步，稳定后再逐步上调。

启动脚本与容器参数

launcher.sh 负责把 Box64、DXVK 与着色器缓存补齐成一套可用配置，并保证不覆盖你在 Winlator 中已经设定好的参数。

行为约定

  • 只补默认值：脚本对已存在的变量使用「未设置才赋值」的写法，Winlator 容器面板里配好的值优先级更高，不会被回写覆盖。
  • 统一入口：命令行启动请走 ./launcher.sh，而不是直接执行 AliceInCradle.exe，否则图形与翻译参数不会生效。
  • 日志位置：容器内启动的 stdout 可直接观察；把它重定向到文件便于反馈问题（但见下方免责说明，不要提交给游戏官方）。
./launcher.sh                       # 使用脚本默认配置启动
AIC_GAME_DIR="$HOME/games/AIC_v030" ./launcher.sh   # 指定游戏目录
BOX64_LOG=1 ./launcher.sh           # 排查期打开 Box64 日志
shell

在 Winlator 中直接使用容器启动

如果你更习惯用 Winlator 的 Start 按钮：先按驱动与性能设置把图形驱动（Turnip）、分辨率和 Box64 参数配好，再把容器内的启动命令指向替换后的 AliceInCradle.exe。此时 launcher.sh 可作为对照调试工具使用。

Termux-X11 / 纯命令行容器

pkg install -y x11-repo termux-x11-nightly
# 在容器里准备好 Wine + Box64 后
export AIC_GAME_DIR="$HOME/games/AliceInCradle_ver030"

shell
注意：Termux 方案需要自行维护 Wine / Box64 与依赖，版本变动更频繁；如果只是想稳定游玩，Winlator 路径更省事。

编译器构建说明

启动器是一段刻意极简的 C 程序，只依赖 kernel32 / user32，因此可以脱离 CRT 直接编译成 Windows PE。

交叉编译（推荐）

参数作用
-O2常规优化，保持体积与行为可预测
-s剥离符号，减小产物体积
-mwindows生成 GUI 子系统 PE，避免出现控制台窗口
-nostdlib不链接 C 运行时，避免在 Wine 下引入额外依赖
-Wl,-e,WinMainCRTStartup指定入口符号，让无 CRT 的产物仍按 Windows 启动约定进入入口函数
-lkernel32 -luser32只链接实际用到的系统库
 
# Debian / Ubuntu
sudo apt install -y clang lld mingw-w64

# Arch
sudo pacman -S mingw-w64-toolchain

x86_64-w64-mingw32-clang --version   # 确认可用
shell

构建自检

file "$AIC_GAME_DIR/AliceInCradle.exe"
# 期望：PE32+ executable (GUI) x86-64, for MS Windows

ls -l "$AIC_GAME_DIR/AliceInCradle.exe"   # 体积应为 KB 量级
shell
常见构建问题：找不到 x86_64-w64-mingw32-clang 说明 mingw-w64 未装或不在 PATH；若报入口符号错误，检查是否漏掉 -nostdlib 与 -Wl,-e,WinMainCRTStartup（两者必须同时给出）。

脚本与工具清单

每个脚本都可独立运行，并支持通过 AIC_GAME_DIR 指定目标目录。

patch_unsafeAssem.py

定位并修补 unsafeAssem.dll 中的运行环境校验逻辑；首次修改前自动生成 .orig 备份，并在修补完成后同步 StreamingAssets/_sha.txt，让完整性检查通过。

python3 patch_unsafeAssem.py                       # 默认目标：$AIC_GAME_DIR
python3 patch_unsafeAssem.py --target /path/to/game # 显式指定目录
python3 patch_unsafeAssem.py --force-skip-sha      # 跳过哈希同步，兼容第三方 Mod
shell
  • --target：目标游戏目录，用于同时维护多个版本副本。
  • --force-skip-sha：不改动 _sha.txt。与自带完整性管理的 Mod 并存时使用，避免两边互相覆盖清单。
  • 回退：用 .orig 覆盖 unsafeAssem.dll，再跑一次 update_sha.py。

unmosaic.py

python3 unmosaic.py            # 修补 Assembly-CSharp.dll
python3 unmosaic.py --restore  # 还原到原始状态
shell

修补的是托管程序集，因此改动后需要同步哈希清单：随后运行 python3 update_sha.py。

update_sha.py

单独重算并同步 StreamingAssets/_sha.txt。适用场景：手动替换过资源、使用了外部 Mod、或多次打补丁后清单与实际文件不一致。

python3 update_sha.py
shell

launcher.sh

容器启动入口：补齐 Box64 / DXVK / 着色器缓存配置后启动游戏，不覆盖容器中已存在的参数。详见启动脚本与容器参数。

src/stub_perfect.c

精简启动器源码，替换原 AliceInCradle.exe 作为 Wine / Box64 下的入口，并透传命令行参数给游戏本体。构建方式见编译器构建说明。

常见问题排查 FAQ

按「完全起不来 → 起来就退 → 进去卡/画面异常 → 补丁不生效」的顺序排查。

启动与崩溃

双击或启动后窗口一闪而过，回到容器界面

先确认是否用了替换后的 AliceInCradle.exe，以及是否通过 ./launcher.sh 启动。若命令行启动，把输出重定向到文件看具体报错：

BOX64_LOG=1 ./launcher.sh > boot.log 2>&1; tail -n 40 boot.log
shell

常见原因是 Box64 内存模型或标志位模拟过松：把 BOX64_DYNAREC_STRONGMEM 调到 1（仍崩则 2）、BOX64_DYNAREC_SAFEFLAGS 调到 2 再试。

提示完整性校验失败 / 资源校验不通过

说明文件已被改动但 StreamingAssets/_sha.txt 没同步。执行 python3 update_sha.py 后重试。若同时使用了自带清单管理的第三方 Mod，改用 python3 patch_unsafeAssem.py --force-skip-sha，让 Mod 侧维护哈希。

启动被拦截，像检测到异常运行环境

这是 unsafeAssem.dll 的环境校验在工作。确认 patch_unsafeAssem.py 已成功执行，且游戏目录里出现了 unsafeAssem.dll.orig。若你复制过旧的 DLL 或做过整目录还原，需要重新打一次补丁。

图形与性能

长时间黑屏、卡在 Unity 启动画面

多数是 DXVK 首次着色器编译。确认着色器缓存路径可写且持久（DXVK_STATE_CACHE_PATH），耐心等待首轮编译完成；反复黑屏则换 Turnip 驱动版本或降低分辨率再试。

贴图错乱、文字缺失、部分特效变黑

典型驱动兼容问题。按顺序尝试：降低分辨率与画质 → 关闭 MSAA / 后期特效 → 更换 Turnip 驱动版本 → 提高 BOX64_DYNAREC_SAFEFLAGS。若只出现在特定场景，可在反馈时记录到 Issue。

能进游戏但帧率很低、发热降频明显

确认走的是 Vulkan / Turnip 路径而非 OpenGL 转发；限制帧率上限、降分辨率与画质；关闭容器内的调试 HUD 与 BOX64_LOG。移动设备温控是主要变量，建议配合散热。

补丁与还原

装了 Mod 之后补丁失效或互相冲突

让哈希清单只有一个维护者。要么用 --force-skip-sha 让 Mod 管理 _sha.txt，要么所有改动完成后统一执行 python3 update_sha.py 重算。两者不要混用。

想完全还原成原始状态

依次：用 unsafeAssem.dll.orig 覆盖 DLL；python3 unmosaic.py --restore 还原程序集；把备份的原始 AliceInCradle.exe 放回；最后 python3 update_sha.py 恢复一致性。最省事的做法仍是整目录用备份还原。

更新游戏版本后补丁还能用吗

补丁针对 v0.30 的可执行文件与 DLL 逻辑，版本变更后偏移与校验点通常会失效。请等待对应版本适配，不要在未验证版本上硬打补丁。

反馈须知：在安卓转译环境下使用本补丁产生的任何异常或崩溃，请勿向游戏官方反馈或提交日志，请提到本仓库 Issues。

原理与技术说明

补丁链路由三处相互配合：入口替换、校验修补、清单同步。任何一处缺失都可能导致起不来。

入口替换：为什么需要精简启动器

原版启动器在 Wine / Box64 下会先做一系列环境探测再启动游戏主体，这条路径在转译层容易触发异常。仓库用 stub_perfect.c 编译出一个极小的 GUI 程序作为新的 AliceInCradle.exe：它只做「按约定继续启动并把命令行参数原样透传」这一件事，并把依赖收敛到 kernel32 / user32，不引入 C 运行时，从而大幅降低转译层的变量。

校验修补：为什么改 DLL 而不是改配置

环境检测逻辑位于 unsafeAssem.dll，没有对外配置开关。脚本采用二进制层面的定点修补：在已验证的版本上定位校验判断，改写其结果，使环境检测在容器内被判为通过。修补前生成 .orig 备份，保证可逆。

清单同步：为什么必须处理 _sha.txt

游戏会按 StreamingAssets/_sha.txt 校验资源完整性。任何被修改的文件都会造成哈希不匹配，从而被判定为异常。因此每次修补后都要让清单与实际文件重新一致——这就是 update_sha.py 存在的原因，也是 patch_unsafeAssem.py 默认会自动同步清单的原因。

与 Mod 的共存边界

场景推荐做法
只用本仓库补丁默认流程即可，脚本自动同步清单
Mod 也修改被校验的资源Mod 装完统一 python3 update_sha.py
Mod 自带清单管理patch_unsafeAssem.py --force-skip-sha
多个 Mod 来源不明先只装本补丁确认能进游戏，再逐个加 Mod 定位冲突源

为什么只锁定 v0.30
