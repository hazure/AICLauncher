一、计划背景与现状盘点

本计划面向 AliceInCradle-Android-Compat-Patch（当前基线版本 v0.30，运行栈为 Winlator 加 Termux-X11、Box64 与 Wine）的下一阶段工程化建设。目标不是把项目推倒重来，而是在既有可用的引导链路上，逐步补齐启动器、模组管理、自愈诊断、持续集成与文档站五个缺口，使项目从“个人可跑通的脚本集合”升级为“他人可复现的开源工程”。

（一）项目既有资产盘点

下表所列为本计划可直接复用的既有资产，后续所有批次均以这些资产为基线，不允许绕过或重做。

| 资产 | 现状 | 在本计划中的角色 |
| :--- | :--- | :--- |
| stub.c 与 stub.exe | 约 3.5KB 纯 C，无图形依赖，直接加载 UnityPlayer.dll 并完成壳层绕行 | 引导注入层的唯一实现，冻结接口，只允许增量式改动 |
| unmosaic.py | 直接修改字节码，覆盖式替换 Assembly-CSharp.dll | 迁移对象：能力改写入托管插件，脚本退居应急通道 |
| patch_unsafeAssem.py | 处理反虚机与早期初始化，作用于本地执行层 | 长期保留在脚本侧，不并入插件体系 |
| _sha.txt 与哈希校验 | 已有校验清单，用于识别版本漂移 | 升级为启动前置阶段的强制门禁 |
| Player.log | 引擎运行时日志，含崩溃特征串 | 监控自愈层的主要观测数据源 |
| 文档站 | 已交付单文件响应式站点，含十章内容 | 文档基线，按第七章清单增补 |
| 持续集成工作流 | 已成文的四阶段流水线设计规范 | 第六章接入环节的实现依据 |
| 文档站自动审查工作流 | 已成文的一行式工作流 | 第七章自动化环节的挂载点 |

（二）本轮计划的定位

本项目在本阶段严格按黑客马拉松原型管理，而非商用级虚拟化引擎。判据是：只求在特定机型、特定运行容器版本、特定游戏版本这三元组组合下稳定复现，不承诺全机型兼容，不做通用兼容层。任何试图一次性解决全量兼容性的改动，都视为超出本计划范围。

这一定位带来的直接收益是，可以按最小可验证单元连续推进，而不必背上回归全部机型的负担；直接代价是技术债会被显式记录在第十章风险登记册中，作为已知缺口长期挂起，直到出现明确需求且前置任务全部验收通过后再处理。

（三）三条不可妥协的工程铁律

1、单一职责原则。引导程序只做引导，绝不因为需要界面而引入任何图形库或配置解析逻辑，一旦引入将直接威胁它在转译环境下的可运行性。启动器、模组管理、监控逻辑一律上移到脚本侧。

2、软编码与零污染原则。所有可开关能力以“文件搬迁加配置”实现，不直接覆盖游戏原始文件；任何时刻都能通过清空插件目录回到纯净状态，避免坏档与哈希不一致。

3、随时可中断可回滚原则。每完成一个任务卡必须形成一次可回滚的提交点并打标签；任何一次派发在验收未通过时，仓库必须仍处于可安全搁置状态，不允许留下半改状态进入主干。

（四）本计划的边界声明

为控制范围，以下事项在本计划内明确不做：不改动上游容器的渲染桥接与容器实现；不自建或裁剪根文件系统；不实现多游戏通用启动框架；不做联机与网络对战能力；不做图形界面，界面套壳列为最低优先级批次，排在自愈与流水线之后，且仅在前序批次全部验收通过后才具备派发资格。

二、总体架构与四层职责划分

（一）架构总则与启动调用链

系统按“塔台与地勤”的关系分层：启动器是塔台，负责查天气、排乘客、看黑匣子；引导程序是地勤牵引车，只做最低复杂度的拉起动作。完整调用链如下。

玩家点击启动 -> launcher.py

+-- 预检      校验 _sha.txt / 托管程序集 / 插件三件套是否就位

+-- 模组管理  按开关双向同步 插件目录

+-- 环境构建  生成转译层环境变量、拼装引擎启动参数

+-- 进程拉起  设定工作目录为游戏根目录 -> 拉起 stub.exe

|               +-- stub.exe -> 加载 UnityPlayer.dll

|                     +-- 引导配置生效 -> 网络组件被优先解析

|                           +-- 插件框架初始化 -> 加载插件目录全部组件

+-- 看门狗    另起线程读取引擎日志尾部 -> 命中特征 -> 生成处置建议

-> 写入启动器处置报告

（二）四层职责与边界

| 层级 | 载体 | 职责 | 明确禁止 | 失效降级 |
| :--- | :--- | :--- | :--- | :--- |
| 外观层 | 暂缺，后续图形库 | 配置录入、模组勾选、画质预设、结果展示 | 不承载任何启动逻辑与路径判断 | 命令行始终可用，界面缺失不影响启动 |
| 逻辑调度层 | Python 启动器包 | 环境校验、模组编排、参数拼装、进程拉起、日志监控 | 不改引导程序源码，不直接改写字节码 | 异常时回退到手工命令启动流程 |
| 引导注入层 | stub.exe | 定位工作目录、透传环境变量、加载引擎动态库 | 不解析配置、不联网、不画界面、不引第三方库 | 引导失败由看门狗报告并给修复指引 |
| 监控自愈层 | 看门狗模块 | 实时读取日志，匹配特征串，给出建议并留痕 | 不静默修改存档或配置文件 | 监控异常时降级为仅打印原始日志 |

（三）插件框架为何不能进引导程序

引导程序当前的价值恰恰在于它小、无依赖、行为可预测。把插件框架注入逻辑与界面代码塞进去会带来三重后果：其一，引导器体积与依赖面急剧膨胀，在转译容器里更易触发加载失败；其二，一旦注入逻辑出错，引导与注入两个环节的故障将无法区分，调试成本成倍上升；其三，失去“清空插件即回到纯净状态”的零污染保证。因此插件框架的引入必须走外部劫持路径，而非改写引导源码。

（四）注入落地方案与文件摆放

采用系统的动态库搜索顺序劫持：把插件框架的三个产物放到游戏根目录，由引导配置项驱动引擎在加载阶段优先解析同名网络组件，从而激活插件框架并加载插件。此方案不需要改动引导程序的任何一行代码。

| 文件 | 摆放位置 | 校验点 |
| :--- | :--- | :--- |
| 网络劫持组件 | 游戏根目录 | 文件存在且版本与插件框架主版本匹配 |
| 引导配置文件 | 游戏根目录 | 搜索路径与目标项指向正确 |
| 插件框架目录 | 游戏根目录 | 核心与插件子目录齐备，插件目录可写 |
| 功能插件组件 | 插件框架插件目录 | 由模组管理按开关动态搬迁，不常驻 |
| 插件框架日志 | 运行期生成 | 看门狗的第二个观测点 |

验证顺序固定为四步：先确认三件套齐备；再启动并确认插件日志生成；然后加载一个仅打印日志的示例插件，确认引擎日志出现插件输出；最后才把功能插件接入。四步任一不通过不得进入下一步。

（五）层间契约约定

层间只通过环境变量、命令行参数与退出码三类稳定接口通信。任何新增通信方式都必须先写入本表并同步到文档站，避免形成隐式约定。

| 契约 | 生产者 | 消费者 | 内容 |
| :--- | :--- | :--- | :--- |
| 环境变量集 | 环境构建模块 | 转译层与图形层 | 图形与兼容调优参数，见第十一章速查表 |
| 引擎参数串 | 环境构建模块 | 引导程序透传给引擎 | 画质与显示参数，例如低画质档位开关 |
| 工作目录 | 进程拉起模块 | 引导程序与引擎 | 强制设为游戏根目录，避免资源与日志错位 |
| 退出码 | 引导程序与引擎 | 看门狗 | 零为正常，非零进入特征匹配分支 |
| 日志文件 | 引擎与插件框架 | 看门狗 | 引擎日志与插件日志双通道 |

三、逻辑调度层设计

（一）模块拆分与职责

| 模块 | 文件 | 输入 | 输出 | 验收方式 |
| :--- | :--- | :--- | :--- | :--- |
| 预检 | preflight.py | 游戏目录与校验清单 | 通过标记或错误清单 | 人为篡改一个文件后应拒绝启动 |
| 配置 | config.py | 启动器配置文件 | 结构化配置对象 | 缺失项回落默认值且有日志 |
| 模组管理 | modmanager.py | 模组开关与清单文件 | 插件目录状态 | 反复启停后目标目录内容幂等 |
| 环境构建 | envbuilder.py | 画质预设配置 | 环境变量字典与参数串 | 打印结果与预设表逐项一致 |
| 进程拉起 | spawner.py | 工作目录与参数 | 子进程句柄 | 工作目录正确且日志路径可解析 |
| 看门狗 | watchdog.py | 日志句柄 | 处置建议与报告 | 注入合成日志能命中全部特征 |
| 入口 | cli.py | 命令行参数 | 一次完整启动流程 | 一条命令从零完成启动 |

（二）配置文件规划

配置以单文件承载，分为五段。原则是：所有魔法数字与路径必须外置到配置中，代码内不允许出现硬编码绝对路径。

[paths]      game_dir   = 游戏根目录

stub       = stub.exe

plugins    = 插件框架插件目录

mods_pool  = 模组仓库目录

[graphics]   preset     = low

hud_debug  = 0

strongmem  = 1

[mods]       unmosaic   = on

unsafe_asm = off

[plugin]     log_output = 插件框架日志路径

require_trio = true

[watchdog]   log        = 引擎日志路径

tail_ms    = 800

auto_action = ask

（三）启动决策流程

def launch(cfg):

if not preflight(cfg):  return 2   # 校验失败直接终止，不进入任何写操作

modmanager.sync(cfg)                    # 幂等同步，不覆盖游戏原始文件

env, args = envbuilder.build(cfg)

child = spawner.spawn(cfg, env, args)

return watchdog.attach(cfg, child)

（四）哈希校验与防污染

预检阶段做双重校验：先比对校验清单中的记录哈希，确认补丁基线未被破坏；再对托管程序集做内容哈希并与已知版本表比对，识别游戏版本漂移。任一不一致时，启动器只报错并给出重跑校验脚本的指引，不自动修复、不自动下载，避免在无人值守时改坏环境。

（五）模组管理双目录方案

用模组仓库目录作为全集、插件目录作为生效区，靠文件搬迁表达开关状态。这从根本上消除了直接覆盖托管程序集导致坏档与哈希不一致的历史痛点。每个模组附带一份清单文件描述元数据。

{

"id": "unmosaic",

"dll": "去码插件组件名",

"min_game_version": "1.04",

"requires_restart": true,

"conflicts": [],

"rollback": "remove"

}

四、监控自愈层设计

（一）日志采集方案

看门狗以独立线程读取引擎日志尾部，采用轮询而非文件事件，原因是转译层之下的文件系统事件通知行为不可靠。轮询间隔默认 800 毫秒，同时保留插件框架日志作为插件侧第二观测点。所有命中与处置都追加写入启动器处置报告，便于事后回溯。

（二）错误特征库与处置动作矩阵

| 特征串 | 判定 | 自动动作 | 是否需确认 |
| :--- | :--- | :--- | :--- |
| 图形指令未处理 | 转译层不支持的图形指令 | 提示清理着色器缓存并切换低画质预设 | 需确认 |
| 引擎动态库未找到 | 工作目录错位 | 重新以游戏根目录拉起 | 自动执行 |
| 访问违例 | 转译层内存模型问题 | 建议提高内存模型强度后重试 | 需确认 |
| 执行引擎异常 | 托管层与运行时不匹配 | 停用全部插件后复现，定位问题插件 | 需确认 |
| 哈希不匹配 | 游戏或补丁版本漂移 | 拒绝启动并输出期望与实际哈希 | 强制终止 |
| 内存分配失败 | 地址空间或显存压力 | 建议停用高开销插件并降低画质 | 需确认 |
| 引导配置未生效 | 注入三件套缺失或位置错误 | 输出三件套期望路径清单 | 需确认 |
| 引擎日志未生成 | 引导层未成功拉起引擎 | 回查引导程序与工作目录，输出诊断包 | 强制终止 |

（三）处置三原则

1、只建议不擅改。除工作目录错位这类无副作用修正外，任何涉及画质、缓存、插件状态的变更都必须先征得确认。

2、动作可回滚。每个自动动作在执行前记录回滚信息到报告文件，确保能一键回到处置前状态。

3、留痕优先。崩溃现场必须先完整归档日志再提示处置，避免修复了但丢了现场。

五、插件体系与模组接口库规划

（一）能力归属划分

| 能力 | 现状 | 去向 | 理由 |
| :--- | :--- | :--- | :--- |
| 画面处理 | 脚本直接改字节码 | 托管插件加运行时补丁 | 可开关、可回滚、不怕版本覆盖 |
| 反虚机与早期初始化 | 脚本处理 | 保留在脚本侧 | 需在引擎启动早期的本地层生效，插件时机不足 |
| 联机能力 | 未实现 | 托管插件 | 依赖托管层事件，天然属于插件域 |
| 画质与参数调优 | 手工命令 | 启动器环境构建模块 | 属于环境编排，不属于游戏内逻辑 |
| 版本校验 | 校验清单 | 启动器预检模块 | 属于启动前置门禁 |

（二）模组接口库最小集

先把最常被复用的类型与钩子点封装成一个可引用的类库，后续他人写插件只需引用该库。首版接口集刻意收敛，只保留四类能力。

核心生命周期    就绪、每帧、退出三段回调

补丁点注册集    常用拦截点集中登记，避免各插件重复探测

诊断采集        统一日志与崩溃上下文，供看门狗复用

版本闸门        按游戏版本裁剪补丁，防止漂移后静默失效

（三）去码能力的重写验证

这是验证整套插件框架是否可用的试金石：任务量大到足以暴露问题，又小到可以在一次派发内独立完成。验收标准不是效果正确，而是关闭插件后游戏行为与文件哈希均回到原始状态，以此证明零污染承诺成立。

六、持续集成接入计划

（一）与任务依赖的耦合关系

持续集成不在项目骨架成形之前编写。当前阶段先以仓库内的协作说明文件记录需求清单占位，待任务卡 T13 验收通过后，目录结构与构建入口同时稳定，此时再落地配置文件，避免为不存在的目录结构编写流水线造成反复返工。

（二）四阶段流水线映射

| 阶段 | 触发或动作 | 本项目落地要点 |
| :--- | :--- | :--- |
| 触发 | 推送到主干或提合并请求 | 并行跑构建；仅主干与标签事件才执行发布 |
| 构建 | 交叉编译、打包、编译托管插件、脚本随包 | 本地层强制把警告视为错误，倒逼代码质量 |
| 测试 | 接口边界测试、脚本自检、界面单元测试 | 任一项非零退出即整条流水线红灯 |
| 发布 | 归档产物并在打标签时创建发布 | 仅标签事件执行，产物含安装包、动态库与说明 |

（三）三条红线的工程化落法

| 红线 | 落到配置的具体做法 | 典型反例 |
| :--- | :--- | :--- |
| 交叉编译架构 | 显式指定工具链文件与目标架构；构建后加一步架构自检 | 在服务器本机架构下直接编译，产物架构错位 |
| 仓库体积控制 | 仓库内仅保留根文件系统清单与校验值，实体首次启动时按需下载 | 把根文件系统提交进仓库，检出与构建直接崩溃 |
| 凭据保护 | 签名库与下载令牌一律走平台密文变量，发布环节加人工审批 | 明文写进配置或日志；一旦推送即视为泄露 |

架构自检是三条红线里最容易被忽略、收益却最高的一项：构建完成后用文件类型探测确认动态库确为目标架构，能挡住编译成功但产物不可用这类最隐蔽的失败。

（四）密钥与凭据清单

| 变量名 | 用途 | 作用域 | 轮换策略 |
| :--- | :--- | :--- | :--- |
| 签名库编码副本 | 还原签名库文件 | 仅发布作业 | 随证书有效期 |
| 签名库口令 | 解锁签名库 | 仅发布作业 | 季度轮换 |
| 密钥别名 | 指定签名密钥 | 仅发布作业 | 随证书 |
| 密钥口令 | 签名时授权 | 仅发布作业 | 季度轮换 |
| 下载令牌 | 根文件系统下载鉴权 | 仅运行期，不进构建 | 泄露即立即吊销 |

签名相关凭据只允许出现在发布作业中，构建与测试作业不应持有任何签名凭据。发布作业额外绑定受保护环境，形成人工审批关口，避免误打标签就直接对外发布。

（五）接入时点与过渡策略

流水线配置在批次六落地，此时目录结构已稳定、构建入口已固定。在此之前，以人工执行等价命令清单的方式维持质量下限，并把每条命令写进仓库脚本目录，后续流水线直接复用同一批脚本，确保本地与自动化行为一致。

八、执行编排与推进次序

（一）编排总则与并行窗口

本计划不设固定工期，推进节奏只由验收结果决定。批次串行推进，同一批次内的任务卡仅在满足并行许可时才可同批发出，全部批次构成一条以验收为闸门的关键链。

关键链次序为：基线冻结 到 注入打通 到 插件改写 到 无头启动器 到 自愈看门狗。链上任一节点验收未通过，后续节点一律不得派发，也不得为规避阻塞而提前做下游任务。

允许并行的窗口只有两处。其一，配置模块、预检、模组管理与环境构建四张卡，在启动器目录结构确定后可并行编写，但不得并行写入同一文件。其二，流水线接入与文档同步两条线，在批次五验收通过后可并行推进。除这两处外一律串行。

禁止并行写入的对象包括配置单文件、启动器入口文件、文档站首页文件与仓库协作说明文件。上述位置涉及多张卡的改动时必须排队执行，逐卡验收、逐卡提交。

任一任务卡受阻时，关键链整体停止推进：先按单张任务卡标准执行流程输出阻塞报告并等待决策，不得以改做下游任务的方式填补空档，也不得把未完成部分折叠进后续提交。

（二）批次与推进次序总表

| 批次 | 目标 | 验收标准 |
| :--- | :--- | :--- |
| 基线冻结 | 现有产物全部入库，建立可回滚起点 | 干净环境检出后能按文档复现一次启动 |
| 注入打通 | 插件框架随引导程序一起运行 | 示例插件在引擎日志中输出 |
| 插件改写 | 画面处理改由运行时补丁实现 | 关闭插件后行为与哈希均回到原始状态 |
| 无头启动器 | 命令行启动器成型 | 一条命令完成校验、同步、启动全流程 |
| 自愈看门狗 | 日志监控与处置建议可用 | 合成日志能命中全部特征并正确建议 |
| 流水线接入 | 自动化构建测试并产出制品 | 推送后自动绿灯，标签触发发布 |
| 文档同步 | 文档站补全并启用自动化 | 七个章节到位，双视口回归通过 |

批次与任务卡的对应关系为：批次一对应 T01 至 T02，批次二对应 T03 至 T04，批次三对应 T05 至 T07，批次四对应 T08 至 T13，批次五对应 T14 至 T16，批次六对应 T17，批次七对应 T18，界面套壳为独立批次且优先级最低。批次一至批次五构成串行关键链，任一环节验收不通过，后续批次一律不得派发；批次六与批次七可在批次五验收通过后并行推进；界面套壳不参与并行窗口。推进以验收通过为唯一节奏依据，不设固定工期，任一环节受阻即整体停止并回退到上一检查点。

（三）单张任务卡标准执行流程

1、开工前只读不改：完整读取本任务卡的输入清单、禁止项与验收标准，复述一次验收判据，确认与上一提交点的差异范围后再动手。

2、每完成一个可验证小步就运行一次该卡的验收命令，不攒到最后统一调试；验收命令未运行通过，不得声明本卡完成。

3、遇到无法定位的问题立即停止并输出阻塞报告，内容包括现象、已排除项、下一步猜测与需要人工决策的具体问题，不得自行扩大改动范围或换方案继续试错。

4、结束前必须形成一次提交并打标签，同时输出三行交付说明：改了什么、还剩什么、下一步第一步做什么。

（四）检查点与回滚机制

检查点机制是本计划对返工风险的唯一硬防线。每个任务卡结束都执行提交加标签动作，标签命名统一为带任务编号的检查点。若某张卡在一次派发内未收敛，执行冻结流程：锁定相关目录、写清当前阻塞与已排除项、关闭该卡的继续派发，直到人工给出下一步决策。所有已封存检查点均可一键回退，未过验收的产物一律不得进入主干。

十二、智能体协作协议

（一）仓库内协作说明文件骨架

在仓库根放置一份协作说明文件，把本计划的硬约束以机器可读的形式固化，使任何一次派发都自带上下文。骨架如下。

# 项目协作约束

## 架构红线

- 引导程序只做引导，禁止引入配置解析、图形与网络依赖

- 模组开关通过文件搬迁实现，禁止覆盖游戏原始文件

- 所有路径来自配置文件，禁止硬编码绝对路径

## 提交纪律

- 每个任务卡一个提交，提交信息含任务编号

- 改动参数或接口必须同次更新文档站

- 禁止未过验收项的产物合入主干

## 待办占位

- 流水线需求记录于此，待任务卡 T13 验收通过后落地配置

（二）派单模板字段

1、任务编号、所属批次与前置依赖，用于回溯执行次序与并行资格。

2、输入清单，明确给出可访问的路径、版本与前置产物。

3、验收标准，必须可自动判定或可由单条命令判定。

4、禁止项，写清不许触碰的文件、不许引入的依赖。

5、回滚方式，说明失败时如何退回上一检查点，以及允许回退影响的最大文件范围。

6、并行许可，标明本卡可与哪些卡同时执行、与哪些卡互斥，以及禁止并行写入的文件清单。

（三）禁止智能体触碰的范围

以下范围在任何情况下不得由智能体直接改动：引导程序源码、游戏可执行文件与资源、签名凭据与配置密文、根文件系统实体，以及任何涉及外部下载源地址的字段。这些位置的修改必须由人工确认并单独提交。

十三、合规与免责边界

（一）四条边界原则

1、不内置不分发。仓库与安装包中不得包含任何游戏本体、美术资源或其他受版权保护的内容，全部资源由用户自行提供。

2、不绕过保护。补丁不规避正版校验与加密保护措施，仅面向用户自行合法取得的游戏副本，运行于用户自有设备。

3、不损害他人。所有能力限于本地运行时行为调整，不涉及联网作弊，不提供影响其他玩家体验的功能。

4、自行承担。发布物显著位置标注免责说明与许可证声明，明确用户所在司法区域的合法性由使用者自行判断。

（二）发布物要求

每次发布的制品必须包含可执行产物、校验值清单、版本兼容说明、免责与许可声明。制品文件名与标签一致，避免用户取用错配版本。文档站同步更新兼容版本组合表，作为唯一权威口径。

十四、结论

本计划的核心不是多做几个功能，而是把一条已经跑通的个人链路，转成四层职责清晰、可回滚、可自动化、可对外交付的工程体系。其中引导注入层保持最小且冻结，逻辑与治理全部上移到可替换的脚本侧，插件框架通过外部劫持接入而不污染基线，持续集成守住架构、体积与凭据三条红线，文档站与代码同变更以维持对外可复现的承诺。

执行上按关键链推进：基线冻结、注入打通、插件改写、无头启动器、自愈看门狗五个批次串行推进，流水线接入与文档同步在关键链验收通过后并行收尾，界面套壳作为最低优先级批次单独排队。推进不设固定工期，验收通过是唯一推进依据；任何阻塞一律整体停止并回退到上一检查点。检查点与回滚机制是本计划最重要的组成部分，它保证项目在任何时刻都可以被安全搁置而不留后患。按此推进，项目能在不留下不可收拾的半改状态的前提下，逐步从可跑通的脚本集合升级为可对外交付的开源工程。
